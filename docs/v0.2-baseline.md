# v0.2 design baseline

The agreed design of Project Shire v0.2: an observability platform for laptop servers and power users. A design change is recorded here before it is implemented.

| | |
|---|---|
| **Audience** | People who run a laptop as an always-on server, and power users who want to see what their machine is doing. The first case served is a Mac that runs Claude Code unattended and is reached from a phone through Remote Control. |
| **Problem** | From another device, there is no single place to see whether the machine is awake and healthy, which services and agents are running, and what is scheduled. |
| **Done when** | A new user with a Mac and Claude Code can install Shire and see the machine and the agent on a phone within five minutes, can add a plugin with one `plugin.yaml`, and the repository contains nothing specific to any one user. |

## Architecture

```
┌───────────────────────────┐
│ browser                   │
│ the status page: Vue 3    │
│ and TypeScript            │
└──────┬─────────────▲──────┘
  requests         page files
  and saved        and API
  settings         responses
       │  port 5190  │
┌──────▼─────────────┴──────┐
│ the monitored Mac         │
│ shire: one process,       │
│ kept running by launchd   │
│                           │
│  ┌─────────────────────┐  │
│  │ server (Flask)      │  │
│  │ checks the key,     │  │
│  │ serves the page,    │  │
│  │ answers the API     │  │
│  └───┬─────────────▲───┘  │
│   writes         reads    │
│  ┌───▼─────────────┴───┐  │
│  │ user directory      │  │
│  │ user-settings/      │  │
│  │ plugins/    data/   │  │
│  └───┬─────────────▲───┘  │
│    reads         writes   │
│  ┌───▼─────────────┴───┐  │
│  │ scheduler           │  │
│  │ runs each plugin on │  │
│  │ its own interval    │  │
│  └──────────┬──────────┘  │
│             │ runs        │
│  ┌──────────▼──────────┐  │
│  │ plugins             │  │
│  └──────────┬──────────┘  │
│             │ inspect     │
│             ▼             │
│  macOS, Claude Code,      │
│  Docker, a vault          │
└───────────────────────────┘
```

- **One process.** Shire collects and serves in a single process and needs no Docker. A container could not read the host's battery or process list.
- **Two one-way flows.** Results flow up: scheduler, `data/`, server, page. Settings flow down: page, server, `user-settings/`, scheduler.
- **No calls between the scheduler and the server.** They share only the user directory, so either can stop without affecting the other.

## Plugins

A plugin is a directory with a `plugin.yaml` that defines what to check, how often, and how to display the result. The directory name is the plugin's ID: lowercase letters, digits and hyphens.

**Built-in checks** need only the YAML file:

| Check | Reports | Requires |
|---|---|---|
| `website` | whether a URL responds, and the response time | `url` |
| `program` | whether a process matching a pattern is running | `match` |
| `port` | whether a port accepts connections | `port`, and optionally `host` |
| `file` | the contents of a JSON or text file | `path` |
| `folder` | the file count and the most recently changed files | `path`, and optionally `pattern` |

```yaml
name: Blog
check: website
url: https://example.com
every: 1m
```

**A script** covers anything else. The directory holds an executable in any language, and the YAML file names it:

```yaml
name: Claude Code
check: script
script: collect.py
every: 30s
```

- Shire passes the script one JSON object on standard input: `plugin`, `name` and `options`.
- The script prints its result in the standard format on standard output.
- Each script runs as a separate process with a time limit, so a failing plugin cannot affect the others.
- A script ending in `.py` runs with Shire's own Python interpreter and can import `shire`.
- `script` can name one file for each operating system, such as `macos: macos.py`. v0.2 includes macOS scripts only.

**Settings available to every plugin:**

| Setting | Meaning | Default |
|---|---|---|
| `every` | the run interval, such as `30s`, `5m` or `1h` | `1m` |
| `timeout` | the time limit for one run | `10s` |
| `enabled` | `false` starts the plugin disabled, until it is enabled from the page | `true` |
| `display` | `list`, `number`, `gauge` or `table` | `list` |
| `watch` | the item keys the status summary watches by default | none |
| `tiles` | the item keys the status summary shows as tiles | none |
| `history` | the item keys for which 24 hours of history are kept | none |
| `description` | one line about the plugin | none |
| `options` | settings of the script's own, passed to it unchanged | none |

An invalid `plugin.yaml` never fails silently. The page shows the reason, such as `plugin.yaml: url is missing`.

**Display names.** A plugin directory can also hold a `names.yaml`, which maps system identifiers to readable names:

```yaml
"com.docker.vmnetd": Docker networking helper
"com.google.keystone.*": Google updater
```

- The left side matches an item's key or name, where `*` matches any text. The right side is the name displayed. The first matching line applies.
- The original identifier stays visible in small type under the display name.
- Each core plugin keeps its `names.yaml` in its own directory. A rename made on the page takes precedence.

## Core plugins

Eight plugins are included. Each has a plain title, and its directory name appears in small type on its widget.

| Plugin | Directory | Reports |
|---|---|---|
| Mac health | `core-os-metrics` | sleep state, battery, temperature, memory, processor, storage, network, heaviest processes |
| Running apps | `core-apps` | open applications, background applications, and background helpers with no application |
| Running scripts | `core-scripts` | scripts and interpreters running outside any application |
| Background services | `core-jobs` | launchd jobs and crontab entries, running or on a timer |
| Docker | `core-docker` | every Compose project and its containers |
| Claude Code | `core-claude-code` | whether it is running, Remote Control, connectivity to Anthropic, sessions, and scheduled jobs |
| What Claude can reach | `core-connectors` | MCP servers and connectors, checked every 15 minutes |
| Obsidian | `core-obsidian` | a folder check, disabled until a vault is configured |

- **The `core-` prefix is reserved,** so a user plugin can never collide with a core plugin added later.
- **Any core plugin can be disabled** from the page, and enabled again. The switch on the page takes precedence over the plugin's own `enabled:`.
- **To override a core plugin,** create a directory of the same name in the user directory, containing only the settings to change. The override is merged setting by setting, and `options` key by key.
- When Docker or Claude Code is not installed, its plugin reports that, and the others are unaffected.

## The standard format

Every plugin result is JSON with the same fields, so one page renders any plugin, and renaming, hiding and watching work on every item.

```json
{
  "plugin": "core-docker",
  "taken": 1764000000,
  "ok": true,
  "items": [{
    "key": "blog",
    "name": "blog",
    "value": "up",
    "state": "good",
    "facts": {"Parts": 3}
  }]
}
```

**Item fields:**

| Field | | Meaning |
|---|---|---|
| `key` | required | unique within the plugin and never changes, so settings survive a restart |
| `name` | required | the name the page displays |
| `original` | | the system identifier, shown in small type under `name` when `name` is a readable replacement |
| `value` | | the current reading, such as `running` or `43` |
| `unit` | | the unit of a numeric value, such as `%` or `ms` |
| `state` | | `good`, `warn` or `bad`; omitted when the item is informational |
| `note` | | one or two lines of plain text |
| `section` | | a heading that groups items |
| `facts` | | details, shown when the item is opened |
| `items` | | child items, such as the containers of a project |

**Field ownership:**

- A script prints `items`, and optionally a `summary`.
- The scheduler adds `plugin`, `taken` and `took_ms`.
- When the thing a plugin checks is absent, `ok` is false with a `reason`.
- When the plugin itself fails, `ok` is false with an `error`.

**Validated on every run.** The scheduler validates each result against the format. A result that fails never reaches the page, and the page shows the reason.

**Defined once.** JSON schemas in `src/shire/schemas` define the standard format, `plugin.yaml`, the settings, the groups and the server's status response. Python validates against them, and the page's TypeScript types are generated from the same files, so the two cannot drift apart.

## User directory

All user data is kept in `~/.config/project-shire`, never in the repository. `SHIRE_HOME` sets a different location. It has three directories, one for each writer, so no component can overwrite another's files. A plugin has a directory of the same name in each.

```
plugins/          written by the user
  <plugin>/
    plugin.yaml     a user plugin, or
                    overrides for a
                    core plugin
    its script, if it has one

user-settings/    written by the page
  <plugin>/
    settings.json   names and choices
  groups.json       groups

data/             written by the scheduler
  <plugin>/
    output.json     the latest result
    history.json    24 hours, where
                    history is kept

key               the access key
jobs.json         jobs scheduled by the
                  agent, which lists
                  them here itself
```

- `plugins/` holds only what the user created. A core plugin has no directory there unless it is overridden.
- `user-settings/` is small and worth backing up.
- `data/` holds only regenerated state and is safe to delete.
- No user data belongs in the directory Shire is installed in, because an update replaces it.

## Server

The server is Flask on waitress. It serves the page, and answers four API requests from the contents of the user directory.

| Request | Response |
|---|---|
| `GET /api/status` | everything in one response: every plugin, its latest result, its settings, and the groups |
| `GET /api/history/<plugin>` | that plugin's last 24 hours |
| `PUT /api/settings/<plugin>` | saves the settings for one plugin |
| `PUT /api/groups` | saves the groups |

A write is validated against the schemas first, and a rejection states the reason in plain words. A write from another origin is refused.

The settings for one plugin are its `settings.json`:

```json
{
  "enabled": true,
  "name": "Containers",
  "items": {
    "blog": {
      "name": "Blog",
      "note": "The public site",
      "watch": true,
      "items": {
        "blog-web-1": {"name": "Web server"}
      }
    },
    "old-project": {"hidden": true}
  }
}
```

Each choice is stored under its item's `key`, and a child item's choices are nested inside its parent's, mirroring the result.

- **Write scope.** The server writes only into `user-settings/`. It cannot add or modify a plugin, so the most a key holder can do is enable or disable an existing one.
- **Access key.** Every request requires a random key, stored in `key` and generated on first run. `shire link` prints a URL that contains it. On first use, the server sets a cookie valid for one year and redirects to a URL without the key.
- **Network binding.** The server listens on port 5190 on all network interfaces, so a device on the same network, or on the same Tailscale network, can open the page. Which networks the machine joins, and what they allow, is the user's responsibility. `--host 127.0.0.1` restricts the page to the machine itself, and `--port` changes the port.
- **Recommended access.** The server serves plain HTTP, so Tailscale is strongly recommended: with `--host 127.0.0.1` and `tailscale serve` in front, the connection is encrypted and the access key never crosses a network in the clear.

## Page

- **Status summary,** at the top, titled *Everything at a glance*: one status line, a bar with one mark for each watched item, and tiles from the plugins that define them. A tile opens the item's details.
- **The status line reports watched items only:** one whose state is `warn` or `bad`, or one that is missing. Any other item in those states appears on its own widget and not in the line.
- **A new installation watches five items:** the Mac awake, the network, Claude Code running, Remote Control on, and Anthropic reachable. A choice made on the page takes precedence.
- **Groups are visual only:** a box with a name and a colour, holding widgets in a chosen order. A new installation has three: Your Mac, Your agent and Docker.
- **One standard widget** renders any plugin from its JSON, as a list, a number, a gauge or a table. A plugin never sends code to the page. Claude Code has a dedicated widget.
- **A disabled plugin does not run and takes no space on the page.** It remains in the plugin list behind the button at the top, where it can be enabled.
- **Groups and widgets fold.** The folded state is stored in each device's browser, so a phone and a laptop can differ.
- **From the page,** a user can enable or disable a plugin, rename a plugin or an item, hide or watch an item, create, rename, recolour and reorder groups, and move widgets between them.
- The page shows 24 hours of history and installs to a phone's home screen.

## Code

| Part | Files |
|---|---|
| The `shire` command | `src/shire/cli.py` |
| Server | `src/shire/server.py` |
| User directory | `src/shire/store.py`, `src/shire/schemas/` |
| Scheduler | `src/shire/scheduler.py`, `plugins.py`, `checks.py` |
| Plugins | `plugins/core-*/`, and their helpers `src/shire/host.py`, `fmt.py`, `script.py` |
| Page | `web/`, built into `src/shire/page` |
| Tests | `tests/`, `web/tests/` |

- **Python,** packaged with a `shire` command: `shire run` runs in the foreground, `shire start` registers it with launchd, `shire stop` removes it, and `shire link` prints the access URL.
- **Flask** serves the page and the API, on waitress, a production WSGI server.
- **Vue 3 and TypeScript,** built with Vite into `src/shire/page`, which is included in the package, so an installed copy does not need Node.js. Only a clone needs it, once, to build the page.

## Out of scope for v0.2

Drag-and-drop arrangement, editing `plugin.yaml` from the page, agents other than Claude Code, Linux, Windows, more than one machine, alerts, and usage limits.
